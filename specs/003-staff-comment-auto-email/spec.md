# Feature Specification: 직원 댓글 뒤 고객 알림 메일 자동 발송

**Feature Branch**: `003-staff-comment-auto-email`

**Created**: 2026-10-28

**Status**: Draft

**Input**: User description: "직원이 위젯 댓글을 달고 10분 동안 Send Email 버튼을 누르지 않으면, 지금 Send Email 버튼과 같은 자동화 메일을 고객에게 자동으로 1통 보낸다. 나눠 달면 마지막 댓글 기준 1통. 10분 안에 직접 누르면 지금처럼 바로 보내고 자동 발송 취소. 자동 발송된 경우 버튼은 켜진 채 남는다. 화면 변경 없음."

## 배경

- 고객이 위젯 티켓에 댓글을 달면 담당 직원에게 메일이 자동으로 간다.
- 직원이 고객에게 보이는 댓글(위젯 댓글)을 달면 고객에게 메일이 자동으로 가지 않는다. 직원이 티켓 상세의 "Send Email" 버튼을 눌러야만 간다. 2025-10-15 "자동메일 발송 버튼 추가"에서 자동 발송을 끄고 버튼 방식으로 바꿨다.
- 직원이 버튼을 깜빡하면 고객은 답변이 달린 줄 모른다.

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 직원이 버튼을 잊어도 고객이 답변 소식을 받는다 (Priority: P1)

담당 직원이 티켓 상세에서 고객에게 답 댓글을 달고 "Send Email"을 누르지 않은 채 다른 일을 한다. 10분 뒤 고객은 "Send Email"을 눌렀을 때와 같은 알림 메일을 받는다.

**Why this priority**: 이 기능의 존재 이유다. 버튼을 잊어 고객이 답변을 모르는 일을 없앤다.

**Independent Test**: 직원 댓글을 하나 달고 버튼을 누르지 않은 채 10~11분 기다려, 고객 메일이 1통 발송되는지 확인한다.

**Acceptance Scenarios**:

1. **Given** 직원이 티켓에 위젯 댓글을 달았고, **When** 10분 동안 "Send Email"을 누르지 않으면, **Then** 10~11분 사이에 지금 "Send Email" 버튼과 같은 메일이 그 티켓 고객에게 1통 발송된다.
2. **Given** 자동 발송이 끝났을 때, **When** 직원이 티켓 상세를 보면, **Then** "Send Email" 버튼은 꺼지지 않고 켜져 있다.
3. **Given** 자동 발송이 끝나 버튼이 켜져 있을 때, **When** 직원이 버튼을 누르면, **Then** 지금처럼 메일이 한 번 더 가고 버튼이 꺼진다.
4. **Given** 자동 발송이 한 번 끝났을 때, **When** 직원이 아무것도 하지 않으면, **Then** 그 뒤로 추가 자동 발송은 없다.

---

### User Story 2 - 나눠 단 답변에도 메일은 1통 (Priority: P1)

직원이 답변을 3분 간격으로 댓글 두 개에 나눠 단다. 고객은 마지막 댓글로부터 10분 뒤 메일 1통을 받는다.

**Why this priority**: 메일이 댓글 수만큼 가면 고객이 귀찮아한다. 사용자가 "마지막 댓글 기준 1통"으로 정했다.

**Independent Test**: 직원 댓글 2개를 몇 분 간격으로 달고, 첫 댓글 기준 10분 시점에는 발송이 없고 마지막 댓글 기준 10분 뒤 1통만 가는지 확인한다.

**Acceptance Scenarios**:

1. **Given** 직원이 14:00와 14:03에 댓글을 달았을 때, **When** 시간이 흐르면, **Then** 14:10에는 보내지 않고 14:13~14:14 사이에 메일 1통만 보낸다.
2. **Given** 자동 발송 뒤 직원이 새 댓글을 달면, **When** 그 댓글로부터 10분이 지나면, **Then** 메일이 다시 1통 간다.

---

### User Story 3 - 직접 누르면 자동 발송은 취소 (Priority: P1)

직원이 댓글을 달고 5분 뒤 "Send Email"을 직접 누른다. 메일은 그때 바로 가고, 10분 시점의 자동 발송은 일어나지 않는다.

**Why this priority**: 같은 내용으로 메일이 두 번 가면 안 된다.

**Independent Test**: 댓글 → 10분 안에 버튼 클릭 → 10분이 지나도 추가 발송이 없는지 확인한다.

**Acceptance Scenarios**:

1. **Given** 직원 댓글 뒤 10분이 지나기 전, **When** 직원이 "Send Email"을 누르면, **Then** 지금처럼 바로 메일이 가고 버튼이 꺼지며, 그 댓글에 대한 자동 발송은 없다.
2. **Given** 직원이 버튼을 직접 눌러 버튼이 꺼진 뒤, **When** 직원이 새 댓글을 달면, **Then** 버튼이 다시 켜지고 새 댓글로부터 10분을 센다(지금과 같은 켜짐 + 자동 발송 예약).

---

### Edge Cases

- **10분 안에 고객이 답 댓글을 달 때**: 자동 발송은 예정대로 한다. 고객 댓글로 인한 직원 메일 발송도 지금처럼 따로 일어난다.
- **10분 안에 티켓을 다른 단계(완료 등)로 옮겼을 때**: 예정대로 보낸다.
- **10분 안에 티켓이 삭제되거나 보관됐을 때**: 보내지 않는다.
- **티켓 고객에게 이메일 주소가 없을 때**: 지금 "Send Email" 버튼과 똑같이 보내지 못하고, 오류로 다른 동작을 막지 않는다.
- **메일 자동화가 꺼져 있거나 없을 때**: 지금 버튼과 똑같이 메일이 가지 않는다. 자동 발송 예약은 한 번 처리한 것으로 끝나고 반복 시도하지 않는다.
- **서버를 다시 켰을 때(배포 등)**: 예정 시각이 지난 예약은 다시 켜진 뒤 확인 주기에 맞춰 1통 보낸다. 빠뜨리거나 두 번 보내지 않는다.
- **서버가 여러 대일 때**: 같은 예약을 두 서버가 동시에 처리해도 메일은 1통만 간다.
- **고객 댓글**: 고객이 단 댓글은 이 기능의 대상이 아니다(예약하지 않는다).
- **위젯 댓글이 아닌 직원 내부 메모**: 고객에게 보이지 않는 글이므로 예약하지 않는다.
- **기능 도입 전에 달린 직원 댓글**: 예약이 없으므로 자동 발송하지 않는다.

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 직원이 티켓에 위젯 댓글(고객에게 보이는 댓글)을 달면, 그 티켓의 고객 알림 자동 발송을 "지금부터 10분 뒤"로 예약해야 한다.
- **FR-002**: 이미 예약이 있는 티켓에 직원 위젯 댓글이 또 달리면, 예약을 "새 댓글로부터 10분 뒤"로 미뤄야 한다(예약은 티켓당 하나).
- **FR-003**: 예약 시각이 지나면 시스템은 1분 안에 그 티켓의 고객에게 지금 "Send Email" 버튼과 같은 자동화 메일을 1통 보내고, 예약을 지워야 한다.
- **FR-004**: 예약 시각 전에 직원이 "Send Email"을 직접 누르면, 지금처럼 바로 보내고 버튼을 끄며, 예약을 지워 자동 발송하지 않아야 한다.
- **FR-005**: 자동 발송은 "Send Email" 버튼의 켜짐/꺼짐 상태를 바꾸지 않아야 한다(자동 발송 뒤에도 켜진 채 유지).
- **FR-006**: 삭제·보관된 티켓의 예약은 보내지 않고 지워야 한다.
- **FR-007**: 같은 예약으로 메일이 두 번 이상 가지 않아야 한다(서버 재시작·여러 서버 포함).
- **FR-008**: 메일 발송이 실패해도(고객 이메일 없음, 자동화 없음 등) 예약은 처리 완료로 지우고 같은 예약을 반복 시도하지 않아야 한다. 단, 메시지 전달 자체가 안 될 때(메시지 서버 끊김 등)는 그 예약을 다음 확인 때 다시 시도한다(예약을 잃지 않게).
- **FR-011**: 티켓을 복사하면 복사본은 자동 발송 예약을 물려받지 않아야 한다.
- **FR-009**: 고객 댓글 → 직원 메일 흐름, "Send Email" 직접 발송 흐름, 고객·직원 화면은 지금과 같아야 한다.
- **FR-010**: 예약 확인은 사이트 속도에 영향을 주지 않을 만큼 가벼워야 한다(예약이 지난 티켓만 바로 찾음).

### Key Entities

- **티켓(Ticket)**: 기존 정보에 "고객 알림 자동 발송 예정 시각"(없거나 하나)이 더해진다. 기존 "메일 발송됨"(버튼 꺼짐 판단) 값은 자동 발송이 바꾸지 않는다.
- **직원 위젯 댓글**: 작성자가 고객이 아닌 위젯 댓글. 달릴 때마다 예정 시각을 새로 정한다.
- **고객 알림 메일 자동화**: 지금 "Send Email" 버튼이 실행하는 자동화. 자동 발송도 이것을 그대로 쓴다(내용·받는 사람 동일).

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 직원이 위젯 댓글을 달고 버튼을 누르지 않은 티켓의 100%에서, 마지막 직원 댓글로부터 11분 안에 고객 알림 메일이 1통 발송된다.
- **SC-002**: 10분 안에 버튼을 직접 누른 경우, 그 댓글에 대한 자동 발송은 0건이다.
- **SC-003**: 직원이 10분 안에 댓글을 여러 개 달아도 고객 메일은 1통이다.
- **SC-004**: 서버 재시작 직후와 서버 2대 동시 동작에서도 예약 1건당 메일은 정확히 1통이다.
- **SC-005**: 예약 확인 작업 1회가 티켓 수와 관계없이 짧게 끝나고(목표 50ms 미만), 고객·직원 화면 응답 속도에 차이가 없다.

## Assumptions

- 10분은 고정값이다(관리자 설정 기능은 범위 밖).
- 자동 발송 메일은 "Send Email" 버튼과 같은 자동화를 그대로 실행한다. 운영 서버에 그 자동화가 켜져 있어야 실제로 메일이 간다(지금 버튼과 같은 조건).
- 직원이 이번 답변만 메일을 안 보내게 하는 기능은 필요 없다(사용자 확인).
- 화면은 바꾸지 않는다(안내 문구 없음, 사용자가 시안 B 선택).
- 확인 주기는 1분이라 실제 발송은 예약 시각부터 최대 1분 늦을 수 있다(사용자 승인: 10~11분).
- 예약 확인은 티켓 서버 스스로 1분마다 한다. 현재 개발 환경에는 플랫폼 공용 예약 작업 서비스(crons)가 없고 운영 배포 여부도 확인되지 않아 그것에 기대지 않는다. 자동화의 "기다리기" 동작도 같은 이유로 지금 이 환경에서 다시 이어지지 않으므로 쓰지 않는다.
