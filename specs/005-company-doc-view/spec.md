# Feature Specification: 우리 회사 문서 본문 보기

**Feature Branch**: `005-company-doc-view`

**Created**: 2026-11-11

**Status**: Draft

**Input**: User description: "위젯 '우리 회사 문서' 본문 보기: 티켓 탭 회사 문서 패널의 각 문서(사용 가능 상태)에 '보기' 버튼을 두고, 누르면 같은 패널이 본문 화면(파일명·올린 사람·날짜 + 챗봇이 실제로 읽는 추출 텍스트 전체, 스크롤)으로 바뀌고 '← 목록'으로 돌아온다. 목적: 담당자가 파일 이름만으로는 어떤 문서가 올라가 있는지 알기 어려워 내용 확인. 원본 파일 다운로드는 하지 않음(서버가 처리 후 원본을 지움). 이미 올린 문서도 서버에 추출 텍스트가 남아 있어 바로 볼 수 있어야 함. 권한: 목록과 동일 — 같은 embed × 같은 회사만, 다른 회사 문서는 열리지 않음. 처리 중·실패 문서는 보기 없음."

## 배경

고객사 직원은 위젯 티켓 탭의 "우리 회사 문서"에서 취업규칙·사규 같은 회사 규정 파일을 올리고, 챗봇은 그 내용을 근거로 답한다. 지금 목록에는 파일 이름·올린 사람·날짜·상태만 보여서, 같은 이름의 문서가 어느 버전인지, 실제로 어떤 내용이 올라가 있는지 확인할 방법이 없다. 원본 파일은 처리 후 보관하지 않으므로 다시 받을 수 없다. 대신 챗봇이 실제로 읽는 글을 그대로 보여 주면 "어떤 문서가 올라가 있는지"와 "챗봇이 제대로 읽었는지"를 함께 확인할 수 있다.

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 올린 문서의 내용 확인 (Priority: P1)

인사 담당자가 티켓 탭 → 우리 회사 문서를 연다. 목록의 "2026 취업규칙.pdf" 옆 **보기**를 누르면 같은 패널이 본문 화면으로 바뀌고, 맨 위에 파일 이름·올린 사람·올린 날짜가, 그 아래에 챗봇이 읽는 글 전체가 스크롤로 보인다. 개정 내용(예: 시업시각 09:30)이 들어 있는지 확인한 뒤 **← 목록**을 눌러 목록으로 돌아온다.

**Why this priority**: 이 기능의 존재 이유다. 이것만으로 "어떤 문서가 올라가 있는지 확인"이 해결된다.

**Independent Test**: 회사 문서 하나가 "사용 가능" 상태인 회사로 위젯을 열고, 보기 → 본문 확인 → 목록 복귀를 해 본다.

**Acceptance Scenarios**:

1. **Given** "사용 가능" 상태 문서가 있는 목록, **When** 그 문서의 보기를 누른다, **Then** 같은 패널에 그 문서의 파일 이름·올린 사람·올린 날짜와 본문 글 전체가 보인다.
2. **Given** 본문 화면, **When** ← 목록을 누른다, **Then** 문서 목록 화면으로 돌아오고 목록 내용은 그대로다.
3. **Given** 이 기능이 생기기 전에 올라가 "사용 가능" 상태인 문서, **When** 보기를 누른다, **Then** 다시 올리지 않아도 본문이 보인다.
4. **Given** 본문이 수백 개 조항인 긴 문서, **When** 보기를 누른다, **Then** 처음부터 끝까지 스크롤로 읽을 수 있고 중간이 잘리지 않는다.

---

### User Story 2 - 회사마다 완전히 따로 운영 (Priority: P1)

회사 문서는 회사마다 독립된 공간(별도 워크스페이스처럼)에 보관·검색·표시된다. A사 공간과 B사 공간은 어떤 경로로도 섞이지 않는다. 본문 보기도 이 원칙을 그대로 따른다: A사 위젯에서는 A사 공간의 문서만 목록에 나오고 본문이 열리며, B사 문서는 존재 자체가 드러나지 않는다.

**Why this priority**: 회사 규정은 회사 내부 자료다. 한 회사의 문서가 다른 회사 화면이나 답변에 섞이면 기능 자체를 쓸 수 없다.

**Independent Test**: A사와 B사에 각각 문서를 올린 뒤, A사 정보로 B사 문서의 본문을 요청해 거부되는지 확인한다.

**Acceptance Scenarios**:

1. **Given** B사 문서, **When** A사 정보로 그 문서의 본문을 요청한다, **Then** 본문이 나오지 않고 "찾을 수 없음"으로 처리된다(문서가 존재한다는 사실도 드러나지 않는다).
2. **Given** 다른 위젯 설정(다른 고객사 연동)에 올라간 문서, **When** 같은 회사 이름으로 본문을 요청한다, **Then** 마찬가지로 찾을 수 없음으로 처리된다.

---

### User Story 3 - 볼 수 없는 상태의 문서 (Priority: P2)

처리 중이거나 처리에 실패한 문서는 아직 읽은 글이 없으므로 보기 버튼이 없다. 목록을 띄워 둔 사이 다른 직원이 문서를 지웠다면, 보기를 눌렀을 때 "이미 삭제된 문서"라는 안내가 나오고 목록이 새로 고쳐진다.

**Why this priority**: 흔하지 않은 경우지만, 빈 화면이나 알 수 없는 오류로 끝나면 안 된다.

**Independent Test**: 처리 중·실패 문서의 행에 보기가 없는지 보고, 문서를 서버에서 지운 뒤 화면에 남은 보기를 눌러 본다.

**Acceptance Scenarios**:

1. **Given** "처리 중" 또는 "실패" 문서, **When** 목록을 본다, **Then** 그 행에는 보기 버튼이 없고 삭제 버튼은 그대로 있다.
2. **Given** 목록이 열린 사이 삭제된 문서, **When** 보기를 누른다, **Then** "이미 삭제된 문서입니다" 안내가 보이고 목록이 최신으로 바뀐다.
3. **Given** 일시적인 연결 문제, **When** 보기를 누른다, **Then** "내용을 불러오지 못했습니다. 다시 시도해 주세요" 안내와 다시 시도 방법이 보인다.

### Edge Cases

- 본문 글이 비어 있는 "사용 가능" 문서(이론상 없어야 함) → "표시할 내용이 없습니다" 안내.
- 본문을 불러오는 동안 → 불러오는 중 표시. 그 사이 ← 목록을 누르면 바로 목록으로 돌아가고, 늦게 도착한 본문이 목록 화면을 덮지 않는다.
- 본문 화면을 보는 중 패널을 닫았다가 다시 열면 → 목록 화면부터 시작한다.
- 본문 글에 표시용 코드처럼 생긴 문자(꺾쇠괄호 등)가 섞여 있어도 → 글자 그대로 보이고, 화면 동작에 영향을 주지 않는다.
- 아주 긴 문서(수만 자) → 화면이 멈추지 않고 스크롤된다.

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 회사 문서 목록에서 "사용 가능" 상태 문서의 각 행에 **보기** 버튼을 보여야 한다. "처리 중"·"실패" 문서에는 보여서는 안 된다.
- **FR-002**: 보기를 누르면 같은 패널 안에서 본문 화면으로 전환해야 한다. 위젯 밖(새 탭·새 창)으로 나가지 않는다.
- **FR-003**: 본문 화면은 파일 이름, 올린 사람, 올린 날짜, 그리고 챗봇이 답변에 쓰는 그 문서의 글 전체를 보여야 한다.
- **FR-004**: 본문 화면에서 **← 목록**으로 문서 목록에 돌아갈 수 있어야 한다.
- **FR-005**: 본문 보기는 회사별 독립 공간 원칙을 따라야 한다. 요청한 위젯 설정(고객사 연동)과 회사의 공간에 속한 문서만 열 수 있고, 다른 공간의 문서는 존재하지 않는 것과 같은 응답을 줘야 한다. 본문을 읽어 오는 위치도 그 회사 공간 안으로 한정해야 한다.
- **FR-006**: 이 기능이 생기기 전에 올라간 "사용 가능" 문서도 다시 올리지 않고 볼 수 있어야 한다.
- **FR-007**: 본문 글은 서식 없는 글자 그대로 보여야 하며, 글 안의 어떤 문자도 화면 코드로 해석되어서는 안 된다.
- **FR-008**: 이미 삭제된 문서, 아직 처리 중인 문서, 불러오기 실패를 각각 구분한 안내 문구로 보여야 한다(한국어·영어).
- **FR-009**: 원본 파일(PDF·한글 등)을 내려받는 기능은 제공하지 않는다.
- **FR-010**: 본문 보기는 문서 목록·올리기·삭제의 기존 동작과 챗봇 답변에 아무 영향을 주지 않아야 한다.

### Key Entities

- **회사 문서**: 한 고객사 연동 안에서 한 회사가 올린 파일 하나. 파일 이름, 올린 사람, 올린 날짜, 상태(처리 중·사용 가능·실패)를 가진다. 사용 가능 상태이면 챗봇이 읽는 본문 글이 서버에 보관돼 있다.
- **본문 글**: 회사 문서에서 뽑아 낸 서식 없는 글. 챗봇이 답변 근거로 검색하는 원천과 같은 내용이다.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 담당자가 목록에서 원하는 문서의 본문을 여는 데 클릭 한 번이면 된다.
- **SC-002**: 195개 조항 분량(약 6만 자)의 문서도 보기를 누른 뒤 3초 안에 본문이 보이고, 끝까지 스크롤된다.
- **SC-003**: 다른 회사·다른 고객사 연동 문서의 본문 요청은 100% 거부된다(자동 시험으로 확인).
- **SC-004**: 기존에 올라가 있던 사용 가능 문서는 100% 다시 올리지 않고 열린다.
- **SC-005**: 본문 화면에서 본 글과 챗봇이 그 문서를 근거로 답한 내용이 서로 일치한다(본문에 있는 조항 내용을 챗봇에 물었을 때 같은 값을 답한다).

## Assumptions

- 볼 수 있는 사람은 지금 목록을 볼 수 있는 사람과 같다(그 회사 정보가 들어간 위젯을 쓰는 직원 누구나). 직원별 권한 구분은 이번 범위가 아니다.
- 본문 화면에서 글자 찾기, 복사 전용 버튼, 인쇄, 원본 서식 재현은 이번 범위가 아니다. 브라우저 기본 텍스트 선택·복사는 막지 않는다.
- 본문은 처리 시점에 저장된 글을 그대로 보여 준다. 문서를 바꾸려면 지금처럼 삭제 후 다시 올린다.
- 일본어 문구는 기존 회사 문서 패널과 같이 이번 범위가 아니다(영어로 보인다).
- 위젯 서버는 기존 회사 문서 목록·올리기·삭제와 같은 방식으로 TeamplGPT에 요청을 중계한다.
- 변경 대상은 두 저장소다: TeamplGPT(본문 제공), okrservice(위젯 서버 중계, 위젯 화면).
