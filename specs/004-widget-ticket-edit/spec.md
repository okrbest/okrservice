# Feature Specification: 위젯 티켓 접수 후 수정

**Feature Branch**: `004-widget-ticket-edit`

**Created**: 2026-11-10

**Status**: Draft

**Input**: User description: "고객이 위젯에서 티켓을 접수한 뒤 수정할 수 없다. 티켓 제목은 수정하지 못하게 하고 나머지(요청 구분·설명·첨부·공개 설정)는 수정할 수 있게 한다. 요청 구분·설명·첨부는 접수 단계(파이프라인 첫 단계)에 있을 때만, 접수한 고객 본인만, 위젯의 진행 상황 화면에서만 수정한다. 수정하면 티켓 활동 기록에 '고객이 수정함'을 남긴다. 화면은 접수 폼을 수정 모드로 재사용하고 제목은 읽기 전용으로 보여 준다. (추가) 공개 설정(회사에 공개/나만 보기)은 단계와 상관없이 수정할 수 있다 — 첫 단계가 지나면 같은 수정 화면에서 공개 설정만 바꿀 수 있고 나머지는 읽기 전용."

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 접수한 티켓 내용 고치기 (Priority: P1)

고객이 위젯에서 티켓을 접수한 뒤, 설명을 빠뜨렸거나 요청 구분을 잘못 골랐다는 것을 알게 된다. 위젯의 티켓 진행 상황 화면에서 "수정"을 누르면 접수할 때와 같은 모양의 화면이 지금 내용으로 채워져 열린다. 제목은 보이기만 하고 바꿀 수 없다. 고객은 요청 구분, 설명, 첨부파일, 공개 설정을 고친 뒤 저장하고, 진행 상황 화면으로 돌아와 바뀐 내용을 확인한다.

**Why this priority**: 요청의 핵심이다. 지금은 잘못 접수하면 댓글로 정정하거나 새로 접수해야 해서 담당자와 고객 모두 혼선이 생긴다.

**Independent Test**: 접수 단계에 있는 본인 티켓의 진행 상황 화면에서 수정 → 저장 후, 위젯과 직원 화면에서 바뀐 내용이 보이고 제목은 그대로인지 확인한다.

**Acceptance Scenarios**:

1. **Given** 고객 본인이 접수한 티켓이 접수 단계에 있을 때, **When** 진행 상황 화면을 열면, **Then** "수정" 버튼이 보인다.
2. **Given** 수정 화면을 열었을 때, **Then** 요청 구분·설명·첨부파일·공개 설정이 지금 티켓 값으로 채워져 있고, 제목은 지금 값이 보이되 고칠 수 없다.
3. **Given** 수정 화면에서 설명과 요청 구분을 바꿨을 때, **When** 저장하면, **Then** 진행 상황 화면으로 돌아오고 바뀐 설명과 요청 구분이 바로 보인다.
4. **Given** 수정 화면에서 기존 첨부 하나를 빼고 새 파일 하나를 붙였을 때, **When** 저장하면, **Then** 티켓의 첨부 목록에 뺀 파일은 없고 새 파일이 있다.
5. **Given** 공개 설정을 "회사에 공개"에서 "나만 보기"로 바꿔 저장했을 때, **Then** 같은 회사 동료의 "회사 티켓" 목록에서 그 티켓이 더 이상 보이지 않는다.
6. **Given** 수정 화면에서 아무것도 저장하지 않고 뒤로 가면, **Then** 티켓은 바뀌지 않는다.

---

### User Story 2 - 처리가 시작된 뒤에도 공개 설정 바꾸기 (Priority: P1)

담당자가 티켓을 이미 다음 단계로 옮긴 뒤, 고객이 티켓에 민감한 내용이 있다는 것을 깨닫고 "나만 보기"로 바꾸고 싶어 한다(또는 동료와 공유하려고 "회사에 공개"로 바꾼다). 진행 상황 화면에서 "수정"을 누르면 같은 수정 화면이 열리고, 공개 설정만 바꿀 수 있으며 나머지 항목은 보이기만 한다.

**Why this priority**: 공개 설정은 처리 내용과 무관하게 고객의 정보 노출을 좌우하므로, 처리 단계와 상관없이 고객이 언제든 정할 수 있어야 한다.

**Independent Test**: 첫 단계가 아닌 본인 티켓에서 수정 화면을 열어 공개 설정만 바뀌는지, 나머지 항목은 고칠 수 없는지 확인한다.

**Acceptance Scenarios**:

1. **Given** 본인 티켓이 첫 단계가 아닌 단계에 있을 때, **When** 진행 상황 화면을 열면, **Then** "수정" 버튼이 보인다.
2. **Given** 그 티켓의 수정 화면을 열었을 때, **Then** 공개 설정만 바꿀 수 있고, 요청 구분·설명·첨부파일은 지금 값이 보이되 고칠 수 없으며, "처리가 시작되어 공개 설정만 바꿀 수 있어요" 같은 안내가 보인다.
3. **Given** 공개 설정을 바꿔 저장했을 때, **Then** 진행 상황 화면으로 돌아오고 바뀐 공개 설정이 반영된다.

---

### User Story 3 - 수정할 수 없는 경우 막기 (Priority: P1)

담당자가 이미 티켓을 다음 단계로 옮겼으면 공개 설정 외의 내용은 바뀌지 않아야 하고, 고객이 남의 티켓을 보고 있으면 아무것도 수정할 수 없어야 한다. 처리 중인 내용이 바뀌어 혼선이 생기거나 다른 사람의 티켓이 바뀌는 일을 막는다.

**Why this priority**: 수정 기능을 여는 순간 함께 지켜야 하는 경계다. 이것 없이 Story 1만 내보내면 처리 중 티켓 내용이 바뀌는 문제가 생긴다.

**Independent Test**: 동료의 공개 티켓, 번호로 조회한 티켓에서 "수정" 버튼이 없는지, 그리고 화면을 거치지 않고 수정 요청을 보내도 거절되는지 확인한다.

**Acceptance Scenarios**:

1. **Given** 같은 회사 동료가 접수한 공개 티켓을 "회사 티켓"에서 열었을 때, **Then** "수정" 버튼이 보이지 않는다.
2. **Given** 첫 단계에서 수정 화면을 연 사이 담당자가 티켓을 다음 단계로 옮겼을 때, **When** 공개 설정 외 항목을 바꿔 저장하면, **Then** 저장 전체가 거절되고 "이미 처리가 시작되어 공개 설정만 바꿀 수 있어요" 같은 안내가 보이며 쓰던 내용은 지워지지 않는다.
3. **Given** 첫 단계가 아닌 티켓에 대해 화면을 거치지 않고 설명 등 공개 설정 외 항목의 수정을 요청했을 때, **Then** 거절되고 티켓은 바뀌지 않는다.
4. **Given** 접수자가 아닌 고객이나 방문자가 화면을 거치지 않고 수정을 요청했을 때, **Then** 거절되고 티켓은 바뀌지 않는다.
5. **Given** 누가 어떤 경로로 요청하든, **Then** 티켓 제목은 이 기능으로 바뀌지 않는다.

---

### User Story 4 - 담당자가 고객 수정 사실 확인 (Priority: P2)

담당 직원이 티켓을 열면, 고객이 접수 후 내용을 고쳤다는 사실과 언제 무엇을 고쳤는지를 활동 기록에서 볼 수 있다.

**Why this priority**: 담당자가 처음 본 내용과 지금 내용이 다를 수 있어 필요하지만, 고객 쪽 수정 기능 자체가 먼저다.

**Independent Test**: 고객이 위젯에서 설명을 고친 뒤, 직원 화면의 티켓 활동 기록에 고객 수정 항목이 생겼는지 확인한다.

**Acceptance Scenarios**:

1. **Given** 고객이 티켓을 수정해 저장했을 때, **When** 직원이 티켓 활동 기록을 보면, **Then** 고객이 수정했다는 항목이 수정 시각과 함께 보인다.
2. **Given** 고객이 설명만 고쳤을 때, **Then** 활동 기록 항목에서 바뀐 항목이 설명임을 알 수 있다.
3. **Given** 고객이 아무 값도 바꾸지 않고 저장했을 때, **Then** 활동 기록이 새로 생기지 않는다.

---

### Edge Cases

- 설명을 모두 지우고 저장하려 하면: 접수할 때와 같이 설명은 필수라 저장할 수 없다.
- 파일을 올리는 중에 저장하려 하면: 접수할 때와 같이 올리기가 끝날 때까지 저장할 수 없다.
- 저장이 실패하면(네트워크·서버 오류): 안내를 보여 주고 수정 화면과 쓴 내용은 그대로 둔다.
- 보관(archive)된 티켓: 수정 버튼이 보이지 않고 수정 요청도 거절된다.
- 새 탭 화면: 수정 버튼이 없다(이번 범위 밖).
- 티켓 번호로 조회한 진행 상황: 번호 조회 메뉴는 지금 첫 화면에서 빠져 있다. 이 경로로 열리더라도 버튼 표시는 목록과 같이 서버의 본인 판정을 따른다.
- 담당자와 고객이 거의 동시에 수정하면: 나중에 저장된 값이 남는다.

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 위젯 티켓 진행 상황 화면은 (a) 보고 있는 고객이 티켓 접수자 본인이고 (b) 티켓이 보관되지 않았을 때만 "수정" 버튼을 보여야 한다. 단계와는 상관없다.
- **FR-002**: "수정"을 누르면 접수 화면과 같은 구성의 수정 화면이 열리고, 요청 구분·설명·첨부파일·공개 설정이 지금 티켓 값으로 채워져야 한다.
- **FR-002a**: 티켓이 소속 파이프라인의 첫 단계에 있으면 요청 구분·설명·첨부파일·공개 설정을 모두 고칠 수 있어야 한다. 첫 단계가 아니면 공개 설정만 고칠 수 있고, 요청 구분·설명·첨부파일은 지금 값을 보여 주되 고칠 수 없으며, 그 이유를 안내해야 한다.
- **FR-003**: 수정 화면은 티켓 제목을 지금 값으로 보여 주되 고칠 수 없어야 한다.
- **FR-004**: 수정 화면은 연락처 입력 등 접수 전용 항목을 보여 주지 않아야 한다.
- **FR-005**: 고객은 수정 화면에서 기존 첨부파일을 뺄 수 있고, 접수할 때와 같은 규칙(허용 형식 등)으로 새 파일을 붙일 수 있어야 한다.
- **FR-006**: 저장 조건(설명 필수, 파일 올리는 중 저장 불가)은 접수할 때와 같아야 한다.
- **FR-007**: 시스템은 저장 요청마다 서버에서 접수자 본인 여부와 보관 여부를 다시 확인하고, 맞지 않으면 거절해야 한다. 공개 설정 외 항목(요청 구분·설명·첨부파일)을 바꾸는 요청이면 첫 단계 여부도 확인해, 첫 단계가 아니면 요청 전체를 거절해야 한다(일부만 저장하지 않는다).
- **FR-008**: 시스템은 이 기능으로 티켓 제목을 바꾸지 않아야 한다. 제목을 바꾸는 입력 자체를 받지 않는다.
- **FR-009**: 시스템은 수정한 설명을 접수할 때와 같은 방식으로 저장해, 위젯과 직원 화면에서 접수 때와 같은 모양으로 보여야 한다.
- **FR-010**: 저장에 성공하면 진행 상황 화면으로 돌아가 바뀐 내용을 바로 보여야 한다.
- **FR-011**: 처리 단계가 바뀌어 거절되면 그 사유를 고객이 알아볼 수 있는 문구로 알리고, 쓰던 내용을 지우지 않아야 한다. 그 밖의 실패도 쓴 내용을 지우지 않는다.
- **FR-012**: 실제로 값이 바뀐 저장마다 티켓 활동 기록에 "고객이 수정함" 항목을 남기고, 바뀐 항목(요청 구분·설명·첨부·공개 설정)을 알 수 있어야 한다.
- **FR-013**: 이 기능은 위젯의 진행 상황 화면에서만 제공하며, 새 탭 화면과 번호 조회 화면에는 수정 버튼을 두지 않는다.

### Key Entities

- **티켓**: 고객이 위젯에서 접수한 요청. 이번 기능에서 고객이 바꿀 수 있는 속성은 요청 구분, 설명, 첨부파일 목록, 공개 설정이다. 제목, 번호, 단계, 담당자는 바꿀 수 없다.
- **티켓 단계**: 티켓이 속한 파이프라인의 처리 단계. 순서상 첫 단계가 "접수 단계"이며, 이 단계에서만 고객이 요청 구분·설명·첨부파일을 수정할 수 있다. 공개 설정은 단계와 상관없이 수정할 수 있다.
- **활동 기록**: 티켓에 일어난 일의 기록. 고객 수정 항목은 수정 시각, 수정한 고객, 바뀐 항목을 담는다.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 고객이 진행 상황 화면에서 수정 버튼을 눌러 설명 한 줄을 고치고 저장하기까지 1분 안에 끝낼 수 있다.
- **SC-002**: 접수자가 아닌 고객·방문자의 수정 시도, 그리고 접수 단계가 아닌 티켓의 공개 설정 외 항목 수정 시도는 100% 거절되고 티켓이 바뀌지 않는다.
- **SC-002a**: 접수자 본인은 티켓이 어느 단계에 있든(보관 제외) 공개 설정을 100% 바꿀 수 있다.
- **SC-003**: 어떤 경로로 요청하든 이 기능으로 티켓 제목이 바뀌는 경우가 0건이다.
- **SC-004**: 고객이 값을 바꿔 저장한 경우 100% 활동 기록에 남는다.
- **SC-005**: 저장이 실패해도 고객이 쓴 내용을 잃는 경우가 0건이다.

## Assumptions

- "나머지 항목"은 접수 폼의 요청 구분, 설명, 첨부파일, 공개 설정을 뜻한다. 연락처는 티켓이 아닌 고객 정보라 범위에서 뺀다.
- "접수자 본인"은 티켓에 연결된 고객 중 위젯을 쓰는 고객이 있는 경우로 판단한다. 같은 회사 동료는 공개 티켓을 볼 수는 있어도 수정할 수 없다.
- 위젯은 로그인 없이 브라우저가 알려 주는 고객 식별값을 믿는 기존 구조(댓글 등록과 같은 수준)를 따른다. 이 신뢰 수준을 높이는 일은 이번 범위 밖이다.
- 담당자에게 따로 알림을 보내지 않는다. 활동 기록만 남긴다.
- 수정 횟수에 제한을 두지 않는다. 접수 단계에 있는 동안은 모든 항목을, 그 뒤에는 공개 설정을 여러 번 고칠 수 있다.
- 동시 수정은 마지막 저장이 남는 방식으로 충분하다.
