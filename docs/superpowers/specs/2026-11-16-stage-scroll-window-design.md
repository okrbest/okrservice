# 티켓 보드 단계 컬럼 스크롤 개선 — 설계

## 의도
보드 단계 컬럼에서 "이전 보기" 버튼 없이 위·아래 스크롤만으로 카드를 오가게 한다.
가장 중요한 조건은 **느려지지 않는 것**: 화면에 그리는 카드 수, 서버 요청 수 모두 지금보다 늘지 않아야 한다.

배경: Sentry Rage Click(JAVASCRIPT-REACT-4) 조사 중, 20개 슬라이딩 윈도우가 통째로 교체되며 스크롤이 맨 위로 튀고,
위로 가려면 버튼 + 서버 재요청이 필요한 점이 불편하다는 결론.

## 목표 / 비목표 / 반목표
- 목표: 위아래 스크롤로 연속 탐색, 보던 카드가 제자리 유지, 위로 돌아갈 때 서버 요청 0
- 비목표: 상한(MAX_ITEMS_PER_STAGE=20) 상향, 서버 코드 변경, 위치 표시("21–40 / 150"), 로딩 표시
- 반목표: 렌더 카드 수 증가, 서버 요청 횟수 증가, 드래그·실시간 업데이트 동작 회귀

## 접근안
| 안 | 서버 요청 | 렌더 카드 | 판단 |
|---|---|---|---|
| 상한 상향(20→100) | 동일 | 최대 100 | 속도 저하 우려로 기각 (사용자) |
| 10개씩 서버 요청 | 2배 (요청당 필터 생성 + RPC 3회 고정 비용) | 20 | 서버 부하로 기각 |
| **받은 카드 보관 + 20개만 렌더, 10개씩 이동** | 동일(20개씩), 위로 갈 땐 0 | 20 | **선택** |

## 설계
1. **보관 목록** — PipelineContext 인스턴스 필드(state 아님, 리렌더 없음)에 단계별
   `loaded`(지금까지 받은 카드 전체, 서버 순서) + `windowStart`(화면 시작 위치) 보관.
   화면 카드 = `itemMap[stageId]` = `loaded.slice(windowStart, windowStart + 20)`.
2. **동기화** — 기존 itemMap 변경 경로(드래그, 추가/삭제, 실시간 반영 등)는 손대지 않는다.
   창을 이동하기 직전에 현재 `itemMap[stageId]`를 `loaded`의 창 구간에 덮어써 맞춘다.
   예외: 창 밖 보관 카드의 실시간 업데이트·삭제는 해당 처리 경로에서 `loaded`도 갱신.
3. **아래로** — 맨 아래 도달 시 `loaded`에 창 뒤 카드가 있으면 10개 이동. 없으면 서버에서 20개
   (skip = `loaded.length`) 받아 `loaded`에 붙인 뒤 10개 이동.
4. **위로** — 맨 위 도달 & `windowStart > 0`이면 `loaded`에서 10개 이동. 서버 요청 없음. "이전 보기" 버튼 제거.
5. **스크롤 위치 유지** — 이동 전 기준 카드의 화면 위치를 기록, 이동 후 scrollTop 보정.
   기존 "아이디가 전부 바뀌면 맨 위로" 동작은 대체.
6. **초기화** — 단계 최초 로드/재조회(필터 변경 포함) 시 `loaded` 리셋.
7. **"더 보기" 버튼** — 유지 (스크롤이 생기지 않는 짧은 컬럼 대비).
8. `stageSkipOffset`은 `windowStart`로 유지 → hasMore, 전체 선택 로직 호환.

## 빌더 판단에 맡김
- 창 이동 계산 순수 함수 파일 분리 + 단위 테스트(widgets jest로 실행)
- 연속 트리거 방지(진행 중 플래그), 보관 목록 메모리 상한 여부
